# CLAUDE.md — Tommy Games

ブラウザで遊べる自作ゲームを 1 つのリポジトリにまとめたモノレポ。
ビルドツールは使わない（HTML / CSS / JS をそのまま配信する）。

**公開URL**: https://oshou35.github.io/tommy-games/

---

## ディレクトリ構成

```
tommy-games/
├── .github/workflows/deploy.yml   # 全ゲームをまとめて GitHub Pages に配信
├── .claude/CLAUDE.md              # このファイル（リポジトリ共通ルール）
├── index.html                     # ゲームランチャー（トップページ）
└── games/
    ├── guild-registration/
    │   ├── game.json              # ランチャー表示用メタ情報
    │   ├── src/                   # ← ここが公開される
    │   ├── docs/
    │   └── .claude/CLAUDE.md      # このゲーム固有のルール
    ├── goki100/
    └── crowd-run/
```

**大原則：ゲーム固有のことは `games/<name>/.claude/CLAUDE.md` に書く。**
このファイルにはリポジトリ全体に効くルールだけを置く。
ゲームを触るときは、必ずそのゲームの `.claude/CLAUDE.md` を先に読むこと。

## 公開URLの決まり方

| 場所 | URL |
|---|---|
| ランチャー | `https://oshou35.github.io/tommy-games/` |
| 各ゲーム | `https://oshou35.github.io/tommy-games/<name>/` |

デプロイ時に `games/<name>/src/` の中身が `_site/<name>/` にコピーされる。
つまり **`src/` の中だけが公開される**。`docs/` や `.claude/` は公開されない。

`src/` の中では**相対パス**を使うこと（`./monsters.json` は OK、`/monsters.json` は壊れる）。

## ゲームを追加する

1. `games/<新しい名前>/src/index.html` を作る
2. `games/<新しい名前>/game.json` を書く

```json
{
  "title": "ゲームの表示名",
  "emoji": "🎮",
  "description": "1行でどんなゲームか",
  "tags": ["3D", "Three.js"]
}
```

3. push する。ランチャーは `game.json` から自動生成されるので、`index.html` の編集は不要

ゲーム固有のルールがあれば `games/<新しい名前>/.claude/CLAUDE.md` に書く。

## バージョン管理ルール

バージョンは **ゲームごとに独立**して `ver. X.Y.Z` 形式で管理する。

| 桁 | 増やすタイミング |
|---|---|
| **X**（左） | クエストによるコード更新 |
| **Y**（中） | クエスト以外の通常アップデート |
| **Z**（右） | バグ修正 |

**リセットルール：**
- X を上げたら → Y・Z を 0 にリセット
- Y を上げたら → Z を 0 にリセット

バージョンはコミットメッセージ・ドキュメントの変更履歴に必ず記載すること。

---

## コミットメッセージルール（リリース通知用）

`main` への push 時に Slack へリリース情報を自動送信するため、
コミットメッセージは以下のフォーマットで記載すること。

```
ver. X.Y.Z: [ゲーム名] 概要（1行）

[add]
- 追加・変更した機能の説明（1件1行）

[fix]
- 修正したバグの説明（1件1行）

[change]
- その他変更（リファクタ・設定変更など）
```

| セクション | 意味 | 記載が必要なとき |
|---|---|---|
| `[add]` | 機能追加 | 新しい機能・ページを追加したとき |
| `[fix]` | バグ修正 | 不具合を修正したとき |
| `[change]` | その他変更 | リファクタ・設定変更など（任意） |

- ドキュメントのみの変更などではセクションを省略してよい
- 箇条書きは体言止めで書く
- **複数のゲームを1コミットに混ぜない**。ゲーム単位でコミットを分けること

### デプロイ前の確認義務（Claude の責任）

`main` への push を行う前に、必ず以下を確認すること。

1. 直近の変更に対して `[add]` / `[fix]` が適切に記載されているか確認する
2. 不足していれば **デプロイ前に** オーナーへ「どの情報が足りないか」「何を書けばよいか」を具体例つきで伝える
3. オーナーが補足・承認してからデプロイを進める

## デプロイ前チェックルール

### 鉄則：コードを変更したら必ずローカルで動作確認してからデプロイする

```
コード変更 → ブラウザ / Puppeteer で確認 → 問題なし → コミット → デプロイ
```

最低限、以下を確認すること。

1. **画面が出るか** — 真っ暗・真っ白・エラー表示になっていないこと
2. **コンソールエラーがないか** — 特に JSX / モジュール読み込みのエラー
3. **相対パスが壊れていないか** — `src/` 配下をそのまま配信するため

React + Babel を使うゲーム（guild-registration など）は、
`<script type="text/babel">` の中身が Babel でトランスパイルできるかを必ず確認する。
構文エラーが出たら **デプロイ禁止**。

> 過去に Fragment 抜けで画面が真っ暗になった事故が発生している（guild-registration ver. 6.0.2 で修正）。

## デプロイ

`main` ブランチに push すると GitHub Actions が自動デプロイ（約1〜2分）。

```
変更 → commit → push origin main → 自動デプロイ → 公開URL反映
```

Slack 通知は `SLACKWEBHOOKURL` シークレットが設定されているときだけ送られる。
未設定なら通知ステップは自動でスキップされる（デプロイ自体は成功する）。

## 指示確認ルール

オーナーから新しい指示・要件を受け取ったときは、**実装前に必ず理解内容をオーナーに言葉で確認する**。

1. 指示を自分の言葉で噛み砕いて説明する
2. 「この理解で合っていますか？」と確認する
3. 承認を得てから実装を開始する

複雑な指示ほど認識のズレが起きやすい。手戻りを防ぐために省略しないこと。

## Claude 学習サポートルール

このプロジェクトはオーナーが **Claude Code の使い方を学ぶ**ために進めている。
そのため、各作業の説明には必ず以下の2項目を含めること。

### 1. 今回使った Claude の機能
使った機能を列挙し、それぞれ一言で何のために使ったか説明する。

### 2. より活用できる Claude の機能（提案）
今回やらなかったが、使いこなせばより効率的・高品質になる機能を「なぜ良くなるか」とセットで提案する。

## ドキュメント更新ルール

**コードを変更したら、そのゲームのドキュメントも同じコミットで更新すること。**

| ドキュメント | 更新が必要なとき |
|---|---|
| `games/<name>/docs/specs/requirements.md` | 機能追加・変更・削除をしたとき |
| `games/<name>/docs/specs/external-spec.md` | 新しいページ・機能のテスト仕様を追加するとき |

1. `requirements.md` のバージョンを上げ、変更内容を変更履歴に追記する
2. `external-spec.md` のバージョンを合わせ、対応するテストケースを追加する
3. コードとドキュメントを同じコミットに含める
